# 录像同步与启动分析

GUI 启动时先将游戏目录的天梯录像复制到当前工作树，再校验缓存或重新提取分析数据。
只复制录像不足以让新对局出现在 GUI：原服务读取的是固定历史 CSV。
因此同步脚本独立提供文件归档，GUI 负责调用既有提取器刷新数据，两者可分别运行。
命令、参数及故障提示见 [GUI 使用说明](../../tools/explorer/README.md)。

## 数据边界

- 默认源目录为已配置游戏目录的 `replays/`；可用本地设置、环境变量或命令行更改，源文件只读。
- 归档遵循 [录像规则](../policy/replay_protocal.md)，以文件头确定模式和地图。
- 只复制 `gameplayID=comp7` 且 `battleType=43` 的天梯录像；“已跳过非天梯”计数表示未复制的录像。
- 同名相同内容跳过；内容冲突不替换已有归档。同步不镜像删除，不复制游戏缓存数据库。
- 运行时归档留在当前工作树，脚本不提交 Git。开发工作树与主工作树各有自己的录像目录。
- 录像仅作为本地输入：`/replays/`、任意位置的 `*.wotreplay` 和 `ReplayCache.db` 均由 Git 忽略。
  分享项目时不提交录像；克隆后由启动同步从本机游戏目录生成归档。
- 临时文件和可能仍在写入的文件延后；下次启动会再检查。不是持续监控，也不会在页面刷新时同步。

## 历史证据与新样本

每次启动使用当前 UTC+08 时间作为分析截止时间，保留历史提取证据，临时 CSV 用后清理。
GUI 只要求审计 JSON 和对局/玩家 CSV，使用 `audit.py --data-only` 跳过分组报告与 SciPy。
独立审计默认仍生成完整统计报告。

被 Git 忽略的 `.drafts/explorer-cache/snapshot.json` 是可丢弃的性能缓存。
复用前校验所有录像的内容 SHA-256、提取代码、历史证据、归档目录的 `ReplayCache.db`，
以及上次实际使用的游戏定义 XML 内容和游戏目录。新增、删除、修改或缓存损坏均触发重建。
即使文件大小和修改时间相同，内容改变也使缓存失效；不将文件时间作为内容相同的证据。
提取期间依赖发生变化或提取内容与当前校验不一致时不发布缓存。
缓存原子替换，写缓存失败不影响本次成功的分析；每次复用重新计算日期窗口、场数与结果计数。
刷新失败时显示空页面和错误提示。只有显式 `--demo` 才加载仓库内的历史研究快照。

历史调查记录只对路径和 SHA-256 均匹配的录像复用。新增无战报录像的实际结果保持未知，
阵亡观测状态保持未调查；每次启动不自动解密分析事件流，也不把历史总体调查计数当成当前筛选计数。
按 2026-10-01 的规定，所有无最终战报对局均假设提前离场，自动参与 30% 胜率情景，
无需先完成事件调查。情景假设与调查事实分开，具体口径见 [分析方法](analysis-method.md)。
